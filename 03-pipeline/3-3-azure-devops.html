3.3) Azure DevOps 연동 (설명 · 실습하지 않음)¶

  • 지도: Source control → Staging → Release
  • 약 5분 (설명)
  • ML Engineer 심화

"로컬 PC에서 Databricks에 연결되면 끝"이 아닙니다. 운영에서는 사람은 코드를 Git에 올리기만 하고, staging·prod 배포는 Azure Pipelines가 서비스 주체로 합니다. 오늘 만든 번들(databricks.yml)과 예시 파일 cicd/azure-pipelines.yml을 환경에 맞게 고쳐 씁니다(아래 "예시 파일을 쓰기 전에 바꿀 것").

연결 지점은 세 곳입니다¶

① 개발Git 폴더 ↔ Azure Repos개발 워크스페이스에서 코드 수정 · 커밋 · 브랜치 push

리뷰Azure Repos PR코드 리뷰 = 승인 지점 ①

② 배포 (CI)Azure Pipelines → staging테스트 · bundle deploy · bundle run

② 배포 (CD)승인 → prod환경 승인 = 승인 지점 ③ · bundle deploy

연결 지점 누가 무엇과 무엇을 인증 설정하는 곳
① 개발 ML Engineer 개발 워크스페이스의 Git 폴더 ↔ Azure Repos 저장소 기본은 내 Microsoft Entra ID 토큰(PAT 불필요) Databricks: Git 폴더 만들기. 관리자: Git URL 허용 목록(dev.azure.com) 확인
② 배포 Azure Pipelines 에이전트 (사내망 자체 호스팅) 에이전트 → staging·prod 워크스페이스 배포용 서비스 주체 + workload identity federation(시크릿 없음) Databricks 계정: 서비스 주체 + federation policy. Azure DevOps: 파이프라인 변수
③ 권한 관리자 서비스 주체 → 카탈로그·Job·Serving Unity Catalog 권한 각 워크스페이스의 UC GRANT, 워크스페이스 권한
  • 로컬 VS Code(Databricks 확장)는 선택입니다. Git 폴더 대신 로컬에서 개발해도 흐름은 같습니다(로컬 → Azure Repos push).
  • Databricks 공식 권장: Git 폴더는 대화형 개발용, CI/CD와 운영 배포는 번들 + workload identity federation.

개발자의 하루¶

  1. 개발 워크스페이스에서 Azure Repos 저장소를 Git 폴더로 엽니다(최초 1회 Workspace → Create → Git folder → 저장소 URL).
  2. 기능 브랜치를 만들고 step3/task_*.py나 resources/*.yml을 고칩니다. dev target으로 내 사본을 배포해 시험합니다(3.1).
  3. 커밋·push 후 Azure Repos에서 PR을 엽니다. 리뷰어가 승인하면 main에 병합됩니다.
  4. 병합되면 파이프라인이 자동으로 돕니다. 개발자는 결과(테스트·staging 실행)만 확인합니다.
  5. prod 배포는 Azure DevOps environment 승인자가 승인하면 진행됩니다.

파이프라인이 하는 일¶

단계 언제 하는 일 승인
CI PR · main 병합 단위 테스트(pytest, Spark 불필요) → bundle validate -t staging → (병합 시) bundle deploy -t staging → bundle run phm_training_pipeline -t staging 승인 지점 ① = PR 리뷰
CD CI 성공 후 environment databricks-prod 승인 → bundle plan -t prod → bundle deploy -t prod --plan plan.json 승인 지점 ③ = 환경 승인
cicd/azure-pipelines.yml (인증 부분 발췌)
pool:
  name: <self-hosted-agent-pool>            # 사내망 안의 자체 호스팅 에이전트
variables:
  DATABRICKS_AUTH_TYPE: azure-devops-oidc   # workload identity federation (시크릿 없음)
...
  - stage: CD
    variables:
      DATABRICKS_HOST: https://<prod-workspace-url>
      DATABRICKS_CLIENT_ID: <prod-sp-application-id>
    jobs:
      - deployment: prod
        environment: databricks-prod        # 이 environment에 승인자 지정
        ...
              - script: |
                  databricks bundle plan -t prod -o json > plan.json
                  databricks bundle deploy -t prod --plan plan.json
                env:
                  SYSTEM_ACCESSTOKEN: $(System.AccessToken)   # 파이프라인 OIDC 토큰 → Databricks 토큰 교환

예시 파일을 쓰기 전에 바꿀 것

  • BUNDLE_ROOT: lab-files는 예시를 만든 폴더 이름입니다. 전달받은 mlops_workshop.zip의 mlops_workshop/ 폴더를 그대로 저장소에 올렸다면 BUNDLE_ROOT: mlops_workshop으로 바꿉니다.
  • 이 예시는 환경 승인 뒤에 bundle plan을 만들고 바로 배포합니다. 승인자가 바뀔 내용(plan)을 먼저 보고 승인하게 하려면 plan을 만드는 단계와 배포하는 단계를 나누고, plan 파일을 파이프라인 산출물로 넘깁니다.
  • <...>로 표시한 워크스페이스 주소·서비스 주체 ID·에이전트 풀 이름을 실제 값으로 채웁니다. 이 예시는 워크샵에서 실행하지 않았습니다.

처음 한 번 설정할 것 (체크리스트)¶

  1. 배포용 서비스 주체를 staging·prod 용으로 하나씩 만들고, 각 워크스페이스에 추가합니다.

  2. 서비스 주체마다 federation policy를 만듭니다(계정 관리자).

    항목 값
    Issuer https://vstoken.dev.azure.com/<Azure DevOps 조직 ID(GUID)>
    Audience api://AzureADTokenExchange
    Subject p://<조직 이름>/<프로젝트 이름>/<파이프라인 이름> 
    databricks account service-principal-federation-policy create <서비스 주체 ID> --json '{"oidc_policy": {...}}'

  3. 서비스 주체에 권한을 줍니다: 대상 카탈로그(ml_staging·ml_prod)의 USE CATALOG·CREATE SCHEMA 등, 번들 경로(/Workspace/Shared/.bundle/...) 쓰기.

  4. 개발 워크스페이스에서 Git URL 허용 목록에 Azure Repos가 들어 있는지 확인합니다.
  1. Azure Repos에 번들 폴더(mlops_workshop/)를 올립니다.
  2. 사내망에 자체 호스팅 에이전트를 준비합니다. Microsoft 호스팅 에이전트는 Private Link로 막힌 워크스페이스에 닿지 못합니다.
  3. 에이전트에 Databricks CLI를 미리 설치하거나 공식 이미지 ghcr.io/databricks/cli를 씁니다. Python 패키지는 사내 미러에서 받습니다.
  4. cicd/azure-pipelines.yml로 파이프라인을 만들고, 단계별 변수 DATABRICKS_HOST·DATABRICKS_CLIENT_ID를 넣습니다.
  5. environment databricks-prod를 만들고 승인자를 지정합니다.

다른 인증 방식

  • Azure Resource Manager service connection(워크로드 ID 페더레이션)으로도 인증할 수 있습니다. 이때는 AzureCLI@2 태스크로 CLI를 실행합니다.
  • 서비스 주체의 OAuth 시크릿(DATABRICKS_CLIENT_SECRET) 방식도 동작하지만, 시크릿 관리가 필요해 Databricks는 workload identity federation을 권장합니다.
