승인 지점¶

오늘은 승인 단계를 실습하지 않았습니다. 승인이 필요하다면 아래 네 곳에 넣습니다.

지점 언제 어디에 넣나
① 코드 승격 학습 코드가 main에 들어갈 때 Git PR 리뷰
② 모델 승격 @champion을 옮기기 전 파이프라인의 promote 앞에 승인 태스크 추가, 또는 deployment job의 approval 태스크(3.2). 승인자는 governed tag 정책으로 제한
③ 운영 배포 prod 워크스페이스에 반영할 때 Azure DevOps 환경 승인 게이트 → bundle deploy -t prod(3.3)
④ 엣지 반영 공장 설비로 내려보낼 때 엣지용 별칭(@edge)을 따로 두고 반영 시점을 운영 서빙과 분리

구축 착수 체크리스트 (기존 .py를 플랫폼에 올리는 순서)¶

  1. 데이터: 학습 데이터를 UC 테이블로 만듭니다(메달리온). 피처 계산은 노트북이 아니라 모듈로 둡니다.
  2. 기존 모델 목록: 형식·위치·라이브러리 버전·입력 컬럼을 정리하고 UC에 등록합니다(2.1). PyTorch 비전 모델(.pth + .yaml)은 모델 클래스 코드와 함께 pyfunc로 묶고, 지금 쓰는 서빙 컨테이너는 시작할 때 UC에서 모델을 받도록 바꾸는 것부터 시작합니다.
  3. 학습 코드: 기존 .py를 features → train → validate → promote 태스크로 나누고, 파라미터는 Job 파라미터로 받습니다.
  4. 모델 형식: 출력 형식(확률·경보·문턱값)을 래퍼로 고정해, 배치·실시간·엣지가 같은 결과를 받게 합니다.
  5. 환경 분리: dev / staging / prod를 UC 카탈로그로 나누고, 번들의 target으로 배포합니다. 운영은 서비스 주체로 실행합니다.
  6. CI/CD: 자체 호스팅 에이전트, workload identity federation, 사내 패키지 미러를 준비합니다.
  7. Genie Code 표준: 팀의 데이터 위치·명명 규칙·금지 사항은 워크스페이스 인스트럭션에, 반복 작업 절차(모델 등록, 학습 Job, 기존 모델 이관)는 스킬로 남겨 Git 폴더에서 관리합니다.
  8. 감시·재학습: 지표 테이블과 정기 재학습 스케줄부터 시작하고, 드리프트 기준 트리거는 그다음에 붙입니다.
