Q1. Databricks 밖(온프레미스 등)에서 학습한 모델을 가져오려면?¶

두 가지 방법이 있습니다. 앞으로 학습할 모델은 ①, 이미 학습해 둔 모델은 ②가 적합합니다.

① Databricks에 직접 기록

외부 학습 환경학습 코드온프레미스 · Kubeflow 등

MLflow 기록Databricks MLflow실험 · 파라미터 · 지표 · 모델

등록Unity Catalog 모델catalog.schema.model · @champion

② 기존 모델 가져오기

내보내기모델 아티팩트외부 MLflow · 파일 서버 · 저장소

전달UC VolumeDatabricks가 읽을 수 있는 위치

검증 · 재기록MLflow Model로딩·추론 코드 · signature · 의존성

등록Unity Catalog 모델@baseline 등 별칭

① Databricks에 직접 기록 ② 기존 모델 가져오기
과정 외부 학습 환경에서 Databricks MLflow로 기록 → UC에 모델 등록 외부 저장소에서 모델 아티팩트 내보내기 → Databricks가 접근할 수 있는 위치에 전달 → MLflow Model로 검증·재기록 → UC 등록
적합한 경우 새 학습 파이프라인을 만들거나 반복 학습할 때 기존 MLflow·Kubeflow 등에서 만든 모델을 옮길 때
주요 고려사항 Databricks 인증·네트워크 연결, UC 권한, 모델 signature 필요. 등록 이름은 catalog.schema.model 형식 가중치 파일만 있다면 로딩·추론 코드와 의존성을 포함해 MLflow Model로 패키징 필요

① 직접 기록하는 코드¶

외부 학습 환경의 MLflow 클라이언트가 Databricks를 기록·등록 대상으로 쓰게 합니다. Unity Catalog 모델은 오픈소스 MLflow Python 클라이언트와 호환됩니다.

import mlflow

mlflow.set_tracking_uri("databricks")      # Databricks MLflow tracking
mlflow.set_registry_uri("databricks-uc")   # Unity Catalog model registry
mlflow.set_experiment("/Shared/external-training")

with mlflow.start_run():
    mlflow.log_param("source", "on-prem")
    mlflow.sklearn.log_model(
        sk_model=model,                     # already trained model
        name="model",
        input_example=X.head(3),            # signature is inferred from this example
        registered_model_name="<catalog>.<schema>.<model>",
    )
확인할 것 내용
인증 외부 환경에는 운영용 서비스 주체를 씁니다. 예: 환경 변수 DATABRICKS_HOST, DATABRICKS_CLIENT_ID, DATABRICKS_CLIENT_SECRET(OAuth)
권한 새 모델: 카탈로그 USE CATALOG, 스키마 USE SCHEMA·CREATE MODEL. 기존 모델에 버전 추가: 모델 소유자이거나 CREATE MODEL VERSION
signature UC의 새 모델 버전에는 signature가 필수입니다. input_example을 주거나 autolog로 기록합니다
autolog Databricks Autologging은 Databricks 노트북 기능이라, 외부 학습 환경과 서버리스 컴퓨트에서는 mlflow.autolog()를 직접 호출합니다
네트워크 모델 파일은 UC가 관리하는 스토리지에 저장됩니다. 학습 환경에서 워크스페이스뿐 아니라 스토리지까지의 경로(사설 엔드포인트·방화벽)도 미리 점검합니다

② 기존 모델을 가져올 때¶

  • 파일(pkl·joblib·ONNX·PyTorch .pth 등)만 있는 경우의 순서와 PyTorch 가중치 패키징 예시는 2.1) 기존 보유 모델 등록에 있습니다.
  • Kubeflow Pipelines 출력이 가중치 파일뿐이면 파일을 UC에 복사하는 것으로 끝나지 않습니다. 모델 로딩·추론 코드를 MLflow flavor 또는 pyfunc 모델로 묶어야 합니다. 반대로 Kubeflow 학습 단계에서 처음부터 MLflow Model을 만들어 ①로 기록하면 가져오기 단계가 줄어듭니다.
  • 등록 후에는 Catalog Explorer에서 버전과 signature를 확인하고, 작은 입력으로 불러와 지금 운영 결과와 같은지 비교한 뒤 별칭을 붙입니다.

Q2. Databricks에서 학습한 모델을 외부(엣지)로 배포하려면?¶

엣지(예: 설비 라인의 PC)를 기준으로 두 가지 방법이 있습니다. 차이는 추론을 어디서 하느냐입니다.

A. 엣지 기기에서 로컬 추론

버전 고정UC 모델배포할 버전 · @edge 별칭

내려받기 · 변환MLflow 형식 / ONNX호환되면 ONNX로 변환

패키징OCI 컨테이너 이미지전처리 · 추론 런타임 포함

전달ACR → 엣지 배포 체계설비 PC에서 판정

B. 엣지 앱에서 원격 엔드포인트 호출

등록UC 모델@champion

서빙Model Serving 엔드포인트Databricks에서 추론

호출엣지 앱REST API 요청 · 응답

A. 엣지 기기에서 로컬 추론 B. 엣지 앱에서 원격 엔드포인트 호출
처리 흐름 UC 모델 버전 고정 → MLflow 형식으로 내려받거나 호환되면 ONNX(Open Neural Network Exchange)로 변환 → 전처리·추론 런타임과 함께 OCI(Open Container Initiative) 형식 컨테이너 이미지로 패키징 → ACR(Azure Container Registry)과 엣지 배포 체계로 전달 UC 모델 등록 → Databricks Model Serving 엔드포인트 운영 → 엣지 앱이 REST API로 요청
적합한 경우 네트워크가 불안정하거나 짧은 지연 시간이 필요할 때 장치가 작거나 모델을 중앙에서 업데이트·운영하고 싶을 때
주요 고려사항 장치의 OS·CPU/GPU·가속기에서 모델 호환성과 성능 검증 필요. Databricks는 UC 모델 파일 다운로드 경로를 제공 추론이 Databricks에서 실행되므로 네트워크 연결과 왕복 지연 시간에 의존. Model Serving은 REST 엔드포인트 제공

A 방식을 쓸 때 챙길 것¶

  • 워크샵의 엣지 시뮬레이터 앱은 A 방식을 Databricks Apps 안에서 흉내 낸 것입니다(4) 배포 3단계). 실제 공장에서는 같은 순서를 설비 옆 PC에서 실행합니다.

  • 모델 파일은 MLflow API로 내려받습니다. 버전 번호나 별칭으로 지정할 수 있습니다.

    import mlflow
mlflow.set_registry_uri("databricks-uc")
mlflow.artifacts.download_artifacts(
    artifact_uri="models:/<catalog>.<schema>.<model>@edge",   # or .../<model>/<version>
    dst_path="/models/phm",
)

  • Unity Catalog는 모델 버전·권한·이력을 관리하는 곳이며, 엣지 장치로 이미지를 배포하는 일까지 하지는 않습니다. 이미지 빌드·서명·배포 파이프라인(ACR, 엣지 런타임 등)을 따로 둡니다.

  • 운영 서빙과 반영 시점을 나누려면 엣지용 별칭(@edge)을 따로 둡니다(승인 지점 ④).
  • 배포 기록(모델 버전·코드 버전·의존성 버전)을 남기고, 엣지에서 판정 결과를 모아 두었다가 연결될 때 올리면 5) 감시와 재학습에 그대로 쓸 수 있습니다.
  • ONNX로 변환하면 변환 전후 예측이 같은지, 대상 장치가 쓰는 연산을 지원하는지 따로 확인합니다.

ONNX를 이용한 엣지 배포 사례 (참고)

Databricks 블로그 Resolving Manufacturing Quality with Machine Vision and MLOps(2025-04-15)는 제조 라인 균열 감지 참조 아키텍처입니다. Databricks에서 YOLO 계열 비전 모델을 학습해 ONNX로 내보내 MLflow·Unity Catalog로 관리하고, 파트너 엣지 런타임이 UC에서 모델을 내려받아 현장 카메라 영상으로 추론합니다. 이상 데이터와 드리프트 감시로 재학습·재배포하는 흐름도 함께 설명합니다.

참고 자료¶

1) 사용자 Docker 이미지로 AI Runtime 작업 실행 (BYOC, Public Preview)¶

Use custom Docker images with AI Runtime (Learn, 2026-11-11)

  • AI Runtime(서버리스 GPU)의 작업을 관리형 환경 대신 직접 만든 Docker 이미지로 실행합니다. 이미지를 워크스페이스의 Databricks Artifact Registry에 올리고, 작업 YAML에 <catalog>.<schema>.<image>:<tag> 이름을 적어 Databricks CLI로 제출합니다.
  • 다른 레지스트리에 있는 이미지는 CLI databricks air images push로 복사할 수 있습니다(Push images with the Databricks CLI). 문서 예시는 Amazon ECR이며, ACR 같은 비공개 레지스트리는 먼저 Docker 로그인을 한 뒤 이미지 주소를 지정합니다.
  • 사용 조건: 워크스페이스 관리자가 Previews 화면에서 Databricks Artifact Registry 미리 보기를 켜야 합니다. Databricks CLI 1.19.0 이상이 필요합니다.
  • 제한: linux/amd64 이미지, 20 GB 미만, 작업을 제출하는 워크스페이스의 Artifact Registry에 있어야 합니다.
  • 이 기능은 실시간 Model Serving 엔드포인트를 사용자 컨테이너로 띄우는 기능이 아닙니다. GPU 학습·배치 작업용입니다.
  • AI Runtime이 홈 리전 밖에서 작업을 실행하면 이미지도 그 리전으로 옮겨집니다. 대상 리전의 가용성과 처리 위치는 Designated Services 표에서 확인합니다.

2) Databricks Autologging¶

  • Databricks Autologging: Databricks 노트북에서 학습하면 파라미터·지표·모델을 자동으로 기록합니다. 서버리스 컴퓨트에서는 자동으로 켜지지 않으므로 mlflow.autolog()를 직접 호출합니다(실습 Step 2도 직접 호출).
  • mlflow.autolog() API (MLflow 3.8.1): 실습 환경(서버리스 환경 버전 5)의 MLflow 버전 문서입니다.
