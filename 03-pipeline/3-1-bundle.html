3.1) 번들로 선언하기 (데모 · ML Engineer 심화)¶

  • 지도: release
  • 약 5분 (데모)
  • ML Engineer 심화

Step 3에서 노트북으로 만든 Job을 Declarative Automation Bundles(구 Databricks Asset Bundles)로 선언합니다. Job 정의가 코드(databricks.yml)가 되어 Git으로 관리하고, 같은 정의를 dev → staging → prod 워크스페이스에 그대로 배포할 수 있습니다.

파일 구성 (mlops_workshop/ 루트)¶

databricks.yml                         # bundle name, variables, targets (dev / staging / prod)
resources/phm_training_pipeline.job.yml  # the 4-task job (same .py files as Step 3)
step1/ step2/ step3/ ...               # code synced to the workspace on deploy
tests/                                 # unit tests run by CI (no Spark cluster needed)
cicd/azure-pipelines.yml               # Azure DevOps example (3.3)
databricks.yml (targets 부분)
targets:
  dev:
    mode: development          # 개인별 접두어 [dev 이름], 스케줄·트리거 일시 중지
    default: true

  staging:
    mode: production           # 검증된 결과물 배포 규칙 적용 (아래 표)
    workspace:
      host: https://<staging-workspace-url>
      root_path: /Workspace/Shared/.bundle/${bundle.name}/${bundle.target}
    variables: { catalog: ml_staging, schema: phm }
    run_as: { service_principal_name: <staging-sp-application-id> }

  prod:
    mode: production
    workspace:
      host: https://<prod-workspace-url>
      root_path: /Workspace/Shared/.bundle/${bundle.name}/${bundle.target}
    variables: { catalog: ml_prod, schema: phm }
    run_as: { service_principal_name: <prod-sp-application-id> }
    resources:
      jobs:
        phm_training_pipeline:
          schedule: { quartz_cron_expression: "0 0 2 ? * MON", timezone_id: Asia/Seoul, pause_status: UNPAUSED }

staging과 prod는 mode가 같은데 무엇이 다른가요?¶

번들의 mode는 development와 production 두 가지뿐입니다. mode는 "개발용인가, 검증된 결과물인가"를 정하는 규칙 묶음이고, 환경 자체를 구분하는 값이 아닙니다. staging은 운영과 같은 규칙으로 미리 배포해 보는 곳이라 production을 씁니다. 환경은 아래 값으로 나뉩니다.

항목 dev staging prod
mode development production production
워크스페이스 개발 스테이징 운영
카탈로그 mlops_edu_dev (각자 스키마) ml_staging.phm ml_prod.phm
실행 주체 (run_as) 배포한 사람 staging 서비스 주체 prod 서비스 주체
리소스 이름 [dev 이름] ... 접두어 접두어 없음 접두어 없음
스케줄 일시 중지 없음 (CI가 bundle run으로 실행) 매주 월 02:00 재학습
배포하는 주체 개발자 (Git 폴더 UI·CLI) Azure Pipelines (CI) Azure Pipelines (CD, 승인 후)

mode: production이 하는 일 (공식 문서 기준):

  • target에 git.branch를 지정하면 그 브랜치에서만 배포되는지 확인합니다(--force로 우회 가능). 오늘 예시는 CI가 main에서만 돌기 때문에 지정하지 않았습니다.
  • 파이프라인이 development: false인지 확인합니다.
  • 서비스 주체로 실행하지 않으면 배포 경로를 특정 사용자 폴더로 덮어쓰지 못하게 하고, run_as·권한을 명시하게 합니다.
  • Databricks는 운영 배포에 서비스 주체를 쓰도록 권장합니다.

데모 순서¶

  1. 워크스페이스의 Git 폴더에서 databricks.yml을 엽니다. 번들로 인식되면 오른쪽에 Deployments 아이콘이 생깁니다.
  2. 대상 dev를 고르고 Deploy → 확인 창에서 Deploy를 누릅니다.
  3. Bundle resources에 [dev 이름] phm_training_pipeline_... Job이 생깁니다. ▶ 아이콘으로 실행합니다.

워크스페이스에서 배포하는 조건

  • 워크스페이스 UI 배포에는 Git 폴더와 서버리스가 필요합니다. 로컬 설치는 필요 없습니다.
  • 다른 워크스페이스(prod)로는 UI에서 배포할 수 없습니다. 운영 배포는 CI/CD가 맡습니다(3.3).
  • Git 폴더를 쓸 수 없으면 웹 터미널에서 databricks bundle deploy -t dev로도 같은 결과를 얻습니다.

템플릿으로 시작하고 싶다면¶

databricks bundle init mlops-stacks 를 실행하면 학습·배치 추론·모니터링 Job과 CI/CD 구성이 들어 있는 표준 MLOps 프로젝트(MLOps Stacks)를 만들 수 있습니다. 오늘 만든 구조는 그 축소판입니다.
